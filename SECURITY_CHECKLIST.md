### Implementation Decisions & Verified Behaviors

1. **Refund Policy on Oversell**:
   When payment is captured but inventory allocation fails in `mark_order_paid` due to concurrent overselling, `/api/razorpay/verify-payment` automatically triggers a full refund via `razorpay.payments.refund(paymentId, { amount, notes: { reason: "Inventory oversold after payment" } })` and returns HTTP 409 to the client.

2. **`updatePaymentStatus` Behavior**:
   `updatePaymentStatus` forbids manually marking orders as `paid`. It only allows admin-initiated refunds (`paymentStatus === "refunded"`), requiring an explicit refund `reason` and calling the Razorpay API before updating the local payment record.

3. **Returns Table Item-Level Data**:
   The existing `returns` table lacks a `return_items` child table. The `apply_return` RPC restores stock for items in the associated order that have a confirmed `sale` inventory log and have not yet had a `return` log recorded, ensuring complete idempotency.
